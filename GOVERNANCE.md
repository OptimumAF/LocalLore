# Governance

## Initial operating model

LocalLore is community-developed and founder-led. **Avery Fernandez (`@OptimumAF`) is the sole initial owner and final decision-maker for the official repository, project direction, accepted contributions, releases, security response, and any delegation of authority.**

This is not currently a foundation, elected committee, or community-controlled organization. Participation is welcome; upstream control has not been delegated. This policy does not claim that GitHub permissions have already been configured. The configuration/evidence checklist lives in `docs/REPOSITORY_SETUP.md`.

## Participation and decisions

Anyone may report reproducible bugs, discuss proposals, contribute documentation, create original story packs, submit patches, and review work. Contributions should be evaluated on correctness, user value, maintainability, privacy, accessibility, and evidence—not identity, popularity, sponsorship, or the number of comments.

Routine changes go through a scoped issue or pull request. Substantial changes need a short proposal/ADR discussing alternatives, migration impact, risks, and tests. Community consensus is useful input, but only the owner decides what is accepted upstream. No vote, bot, agent, or contributor rank can override that decision.

The owner may accept, reject, defer, revert, or request changes to a contribution, with a brief explanation when practical. The project makes no guaranteed response or merge-time commitment.

## Permission boundaries

Contributors begin with the rights GitHub gives the public: viewing, forking, and submitting contributions. No additional repository access is granted automatically. Reviews are advisory unless the owner explicitly delegates a named responsibility.

Only the owner initially controls merges, repository administration, security settings, signing credentials, releases, publishing accounts, and access invitations. Do not give autonomous agents broad administration credentials. Automated checks may report results; they may not approve their own authority or release code.

Any delegation must be recorded here in a reviewed change identifying the person, exact scope, duration if applicable, and revocation process. A future council or foundation requires an explicit owner-approved governance change. Community involvement is not an implied promise of future control.

## Open-source rights are separate

The owner's authority applies to the official upstream project. The Apache-2.0 license grants rights to use, modify, and redistribute under its terms. Forks do not need upstream permission merely to exercise those rights, and upstream governance cannot withdraw rights already granted under the license. Contributions do not transfer their authors' copyrights merely by being accepted. See `LICENSE` and `docs/LICENSING.md`.

## Maintainer accountability and conduct

Use public proposals for normal design decisions and private reporting for sensitive security or conduct matters where a verified channel exists. Do not expose private player stories or personal information to resolve a dispute. The code of conduct applies to project spaces, including the owner. The owner remains the initial enforcement authority; this document does not invent a separate appeals committee.

The project has no automatic succession rule. Any ownership transfer, new administrator, license transition, or formal governance expansion must be explicitly documented and authorized. It is better to mark a project inactive than imply unsupported community control.
