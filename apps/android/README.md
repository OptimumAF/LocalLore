# LocalLore Android shell

M03.02 is a minimal Compose surface with a **local fixture adapter**. It does not
load an LLM, call Rust/JNI, persist a story, or implement gameplay rules in Kotlin.
The UI says this explicitly. M03.03 replaces the sample gateway with the native
engine boundary; M04 adds persistence. The four fixed samples are generated by
the actual Rust host engine and checked for drift.

## Prerequisites and build

- Java 17; set `JAVA_HOME` to its installation.
- Android SDK platform 36 and Build Tools 35.0.0; set `ANDROID_HOME` or an ignored
  `local.properties` with your own SDK path.
- An authorized Android emulator. Both targets tested for this packet run API 35.

From `apps/android/` on Windows (use `./gradlew` on Unix):

```powershell
.\gradlew.bat :app:assembleDebug :app:assembleDebugAndroidTest :app:testDebugUnitTest :app:lintDebug --no-daemon
.\gradlew.bat :app:connectedDebugAndroidTest --no-daemon
.\gradlew.bat :app:installDebug --no-daemon
```

The connected test task installs the debug app and test APK on connected targets.
Use only authorized test devices/emulators. To select one target, set
`ANDROID_SERIAL` to its local ADB transport identifier before running the task;
omit identifiers from public reports. No physical phone was available here.

First-time wrapper/SDK/Maven provisioning needs network access. After provision,
append `--offline` to build/test tasks to use cached dependencies. The installed
app needs no network or account; it requests no platform network/media/contact/
location permission. AndroidX adds its app-owned signature permission for safe
dynamic receivers. No analytics or remote collector is included. Backup/transfer
exclusions are configured, but OS backup behavior is not qualified by this test.

The Gradle wrapper distribution and wrapper JAR match their official SHA-256
checksums. Kotlin/compiler/AGP/Compose versions are explicit; the resolved debug
and test dependency graph is in `app/gradle.lockfile`. Preserve applicable
dependency notices; no license resources are blanket-excluded. Extending build
configurations may require intentionally updating locks with `--write-locks`.
See [toolchain and SDK rationale](../../docs/android/TOOLCHAIN_2026-10-22.md),
[source inventory](../../docs/android/DEPENDENCY_SOURCES.json), and
[review](../../docs/android/REVIEW_2026-10-22.md).

## Exercise the sample

Launch LocalLore. Give the potion to Mira, try giving it again, and try the
unlearned ability. The fixed outcomes show a successful transfer followed by
safe inventory/ability rejections. The **Demo responses** selector exercises
malformed, rejected, delayed and failing proposal responses. Cancel a delayed
response or reset the sample while it is pending; neither may apply the old
completion. Only accepted results enter the transcript.

The ViewModel retains accepted sample state through activity recreation.
Pending work is cancelled on `onStop`, including rotation/backgrounding, and
disposal invalidates callbacks. Process death starts a fresh sample; there is no
restart-durable save, user story input, branch library or claim of real engine
execution in Android. Simulated delay is not a performance result.

## Keep fixtures tied to Rust

From the repository root:

```powershell
cargo run --locked --offline -p locallore --example android_fixtures -- --check
```

To regenerate after an intentional contract change, capture the example's UTF-8
stdout without `--check` into
`apps/android/app/src/main/assets/lantern_quay_cases.json` (no BOM; LF newlines),
then rerun `--check`, host tests and Android tests. The exporter resolves each
case with the existing engine, stores exact request/proposal/receipt provenance,
and derives the displayed projection from the accepted staged engine state.

`RecordedDemoGateway` only matches known raw proposal samples to their recorded
Rust results and rejects all other outputs. It is deliberately finite and
replaceable, not an independent rule engine or an authority for arbitrary model
output. No actual native serialization/callback/resource ownership claim is made
until M03.03 is implemented and tested.

## Checks and remaining gates

JVM tests exercise state publication, duplicate taps, failures, late completion,
cancel/reset and ViewModel disposal. Instrumentation covers actual launch,
fixture permissions/version/scope, accepted/rejected/malformed/failed flows,
cancel/reset, recreation and a small viewport at doubled font scale. The dated
[verification report](../../docs/android/VERIFICATION_2026-10-22.md) records exact
results. The APK includes AndroidX's native graphics-path helper; host ZIP/ELF
alignment checks are not a 16 KiB device qualification or an ARM64 runtime test.

No release APK, publication, repository/Actions setting or merge is part of this
packet. Full M03, production runtime choice, physical testing, durability,
accessibility qualification and narrative quality remain separate gates.
