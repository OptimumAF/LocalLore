## Concrete independent findings

1. `author-controller.ts::follow` calls synchronous `patch({operation:status})`, then `finish` without rechecking current identity. `finish`'s terminal-error branch has no current check. A subscriber calling `contextChanged(newRoot)` during that notification resets the presentation, but the old terminal error then overwrites the new root. A same-root session/head change can also have its freshly set uncertain state cleared by the old terminal error. `run`'s pre-start guard and the earlier context-key fixes do not cover this post-notification edge. Minimal source reproducer: prepare or lookup returns a synthetically valid terminal Busy status; subscriber changes context exactly when operation first becomes non-null; the retired work must not publish its error afterward. Disposing at the same point is a positive closure case.

2. Successful commit/lookup completion checks current identity before its completion patch, but `patch` synchronously notifies navigation/disposal subscribers. The following `effects.refreshLibrary()` executes without another current check. Minimal reproducer: subscribe to status becoming complete, then change scope/session or dispose; refreshed count must remain zero. Live positive controls still require exactly one refresh, the actual decoded outcome retained, and no automatic child opening. This is an obsolete presentation/IPC side effect, not a demonstrated canonical corruption or knowledge grant.

3. A valid prepared preview can be abandoned by read-only lookup. `lookup`/`startWork` retain the preview; `finish` clears it on found/not_found without calling discard. Native `AuthorManager` keeps at most four capabilities for600 seconds. Repeating prepare→lookup can fill those four slots even though no preview remains owned/displayed, making later preparation fail until TTL. The frozen public-observable oracle allows either explicit retention of the visible owned token or exactly one discard when it disappears; it does not require consuming it as a commit. The final bounded mock-capacity case demonstrates the proposed sequence without implementing Store/native authority. This is a bounded ownership/resource leak, not a native authority bypass.

These findings are distinct from the separately owned Main shared-operation admission F1/F2 cases. No change to their predicates/tests is proposed here.
