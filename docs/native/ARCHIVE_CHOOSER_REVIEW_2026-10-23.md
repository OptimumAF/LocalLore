## Provider permission and authority boundary

The [ContentProvider.call API/source](https://android.googlesource.com/platform/frameworks/base.git/+/master/core/java/android/content/ContentProvider.java) makes custom permission enforcement the implementation's responsibility: the framework cannot infer whether an opaque custom method reads or writes data. Therefore bounded test-only setup/stats/readback calls must authenticate the actual Binder caller UID before accessing or mutating fixture state. Neither an extras-supplied package/UID nor a custom control method substitutes for a document URI grant. Reject unexpected methods/arguments and bound input/output bytes; do not expose a generic path/file or arbitrary document mutation interface.

The [DocumentsProvider API](https://developer.android.com/reference/android/provider/DocumentsProvider) requires its call superclass implementation first; custom behavior is allowed when that returns null. The manifest must protect the exported provider with MANAGE_DOCUMENTS and enable URI grants. Actual document create/open operations should pass through DocumentsUI and its narrow grants, without adopting broad permissions during product I/O. These are separate from authenticated synthetic fixture controls. No same-UID compromise or universal external-provider guarantee is implied.

Existing MainActivity uses OpenDocument and CreateDocument callbacks into the retained ShellViewModel/controller. Import bytes must be read and validated before any explicit confirm; a native prepared token, not a Kotlin preview or selected URI, authorizes commit. Export must capture the exact native bytes and show full-private disclosure before picker consent. Existing writer uses the same regular, empty, seekable rw descriptor with no truncation/delete fallback; bounded actual reads ignore metadata size as authority. The selected provider may sync plaintext externally, and a partial newly created document can remain on failure/cancellation.
