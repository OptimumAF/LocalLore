## Proposed parent retention, not implemented deletion

Required ancestry retention fits the accepted representation better than casually materializing or re-scoping inherited history. Original receipts/envelopes retain source branch identity, event sequence, witnesses and provenance. The selected child's returned history/context must remain byte-equal and preserve fork cutoffs; temporary ancestor validation content must not enter that child's eligible context. Existing turns and archive replay explicitly cap an intermediate ancestor at max(its own birth fork, next child's fork). Therefore a retired parent born at8 with a retained child rewound to3 still requires its birth boundary and enough earlier ancestry to validate that creation. Trimming merely to the largest child fork3 corrupts lineage. Compute requirements from direct retained children plus the parent's own birth floor, trim only completed receipt boundaries, and remove corresponding unreachable normalized rows without copying them under a child's scope.

A retirement row must distinguish internal ancestry from a playable target. Public resume, turns/status/drafts/commit/cancel, forks including the existing-child retry fast path, derived-memory publication/read/search and cached Host work must not grant a retired target. Internal replay must still traverse its retained prefix. Physical GC of a now-unneeded retired chain must not erase the persistent deleted-ID tombstone and let an old ForkRequest recreate that operation identity on retry after reopen. Bound tombstones under churn and preserve them through exports. Native mutation gating needs targeted retired/GC scope invalidation while retained child/sibling sessions remain valid, rather than unnecessarily invalidating the entire story. Same-ID/new-draft and stale cached Ready cases remain substantive native acceptance checks.

Archivev1 has no retirement metadata and imports every listed branch as playable. Exporting a retired ancestor as an ordinary v1 branch would resurrect it. Safe retention therefore needs a versioned representation carrying retired ancestry and deleted IDs, or an explicit refusal; silent v1 omission/normalization is insufficient. Schema3 must coordinate strict schema verification, initialization, backup-required/nonoverwrite/rollback migration, read-only old-version behavior, Host's separate workspace-v1 contract and Android's exact database-schema check. Retain explicit v1 compatibility fixtures while adding v2 roundtrip/hostile-retirement checks; changing source schema/archive versions also affects current generated platform-roundtrip goldens. These are outstanding M08.05 dependencies, not implemented or verified behavior. No leaf-only deletion substitute is proposed.

## Actual Android prerequisite and frozen catalog contract

The accepted DurableGateway.snapshot has two independent source-visible child-resume failures: it requires every inherited receipt request scope to equal the selected child, and it then searches root-only workspace.stories for that child. Valid Rust child replay retains ancestor scopes, and the root library intentionally does not list child rows. Repairing the adapter and providing a validated branch catalog is a concrete prerequisite for testing parent retention through Android. No actual red device run is claimed at this checkpoint.

The frozen Store catalogv1 contains story/title/root plus deterministic branch rows with original scope, parent, fork revision, current revision and draft count. It must validate every branch via actual replay in one SQLite read transaction, enforce existing depth/256-branch limits and a64KiB serialized bound, reject unknown/malformed/cyclic metadata, and observe cancellation. Branches may rewind before their parent's birth; graph shape validation must not invent a monotonic fork-time restriction. Catalog data is metadata, not canonical authority and not a new inference or SQL capability.

Android should derive selected child metadata/drafts from this catalog while keeping the library root-only. It must preserve original same-story receipt scopes and exact selected/player scope/head checks without implementing Rust's eligibility rules in Kotlin. A concurrent head change should fail closed or require refresh, not combine metadata from different revisions into a successful snapshot. The selector must bind an immutable rendered catalog/query identity, enforce current-story membership and busy/archive/deletion/recovery/disposal guards, and reject old callbacks across refresh/story switches. Whole-story deletion from a selected child still uses the catalog's original root scope and root head, not the child's revision. Root/child/sibling continuation, retry, unchanged other timeline/knowledge state and root-bound deletion remain execution gates.
