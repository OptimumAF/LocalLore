## Actual SQLite mechanism and pinned compatibility

[SQLite's page-limit documentation](https://www.sqlite.org/limits.html#max_page_count) specifies Full on growth beyond the page cap. [Unused pages](https://www.sqlite.org/pragma.html#pragma_freelist_count) and [auto-vacuum behavior](https://www.sqlite.org/pragma.html#pragma_auto_vacuum) explain how freed pages can satisfy later inserts without raising the cap or shrinking the file. [DROP TABLE](https://www.sqlite.org/lang_droptable.html) removes its table and associated objects. A padding table with no foreign keys, triggers, indexes or AUTOINCREMENT avoids secondary schema objects/actions. No VACUUM, database copy, global disk filling or quota/setting change is required or permitted here.

The pinned `libsqlite3-sys 0.38.2` bundles SQLite `3.53.2`; its MIT package and SQLite's [public-domain deliverable](https://www.sqlite.org/copyright.html) are unchanged. The existing build script accepts `LIBSQLITE3_FLAGS` definitions and tracks their changes. `SQLITE_MAX_PAGE_COUNT` initializes each Pager's default. A platform/helper connection needs its own verified cap; setting that connection's cap does not alter the live Rust Pager. Both limits must be recorded honestly. Existing Kotlin/Android/Compose/Gradle dependencies suffice; no new dependency/runtime selection follows.

CREATE/DROP legitimately changes SQLite internal schema/data counters. Restored application schema means exact original schema definitions plus unchanged application ID, user version and journal policy; it does not mean a byte-identical file or restored internal `schema_version`. Never set schema_version or other internal counters back to old values. Temporary schema divergence remains visible in the report even after successful removal.

## Calibration and ownership requirements

Use one-shot fill and remove processes. Each must close every cursor/connection, finish transactions and exit successfully before the parent makes the next Host/native call. This avoids a held writer reservation accidentally testing Busy instead of Full. Distinct processes avoid the separate-linked-SQLite Unix locking problem previously identified in the contention fixture. Process/token/path validation, fixed SQL vocabulary, bounded rows/blob bytes/steps/output/waits, exact owned handles and known reader/reap completion remain mandatory. Unknown helper state must retain the root and stop further dispatch; a second cleanup call must not silently turn unknown ownership into success.

Before mutation require exact expected application identity/schema/journal/page size/auto-vacuum and a previously absent fixed padding table. Only that test-owned table may be created/filled/dropped; canonical application tables and metadata are never written by the helper. The remove operation must establish ownership and exact schema restoration, close/exit, and expose only fixed protocol categories/counts to public evidence. No arbitrary SQL or caller-selected object name belongs in the protocol.

Page count at the proposed cap with zero freelist pages is not enough by itself: existing Btree cells may still have room. Calibration must observe unmodified actual Rust Full on the target gift commit and unchanged accepted player view/receipts. It must retain the same live owner/session/scope/key and Ready result, then remove padding and recover that exact result once, without another submit or prepare. Repeated recovery must return the same receipt and cannot duplicate the potion transfer. Except for the explicitly permitted host rejection control, only after schema restoration may a new owner verify/reopen and compare accepted history. Ready-before-padding is now frozen; it does not qualify submit/prepare under pressure.

If temporary schema divergence is unacceptable for the intended acceptance criterion, this mechanism cannot satisfy that stronger criterion. TEMP/attached databases do not consume the main database's capped Pager; an external pragma cannot raise the Rust owner's quota. A separately reviewed adjustable owner/VFS capacity-test binary would be an alternative, with a different implementation and evidence scope. Ordinary authorized test work requires no new blanket user approval, while privileged/global storage changes remain excluded.
