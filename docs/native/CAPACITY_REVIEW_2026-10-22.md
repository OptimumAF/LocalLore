## Mechanism and dependency verification

Current [official SQLite limits](https://www.sqlite.org/limits.html#max_page_count) specify SQLITE_FULL when a growth request exceeds the configured page limit. A lower `SQLITE_MAX_PAGE_COUNT` therefore provides actual SQLite capacity failure in a deliberately different native binary. It does not fill a device partition. The [pragma documentation](https://www.sqlite.org/pragma.html#pragma_max_page_count) also states that a requested cap cannot fall below the existing database size. Page size, schema and payload growth matter; choose the profile from actual bounded calibration rather than an assumed row count.

Inspected the pinned `libsqlite3-sys 0.38.2` source and its bundled SQLite `3.53.2`. Its build script accepts whitespace-separated `-D`/`-U` definitions in `LIBSQLITE3_FLAGS` and tracks changes to that environment variable. The amalgamation initializes each new Pager's `mxPgno` from `SQLITE_MAX_PAGE_COUNT`; its pragma setter changes the executing Pager. An external Android connection cannot set a persistent quota for the Rust owner. Reopening this capacity binary recreates the same default cap, so it does not demonstrate relief or same-key accepted recovery.

The pinned binding crate declares MIT; the [SQLite deliverable is public domain](https://www.sqlite.org/copyright.html). Changing the compile definition introduces no new runtime library or license selection. Keep existing notices and dependency pins. Current upstream documentation can describe a later SQLite version, so the reviewed pinned amalgamation remains the binary-specific authority.
