## Additional allocation research, 2026-10-25

This section preserves the earlier snapshot and adds only the separately authorized small filesystem experiment under [claim6401417176](https://github.com/OptimumAF/LocalLore/issues/9#issuecomment-6401417176). **NTFS compression is feasible on the new tiny files; complete AVD allocation, QEMU IO and SDK admission remain unqualified.** No emulator or model operation followed this result.

Microsoft documents per-file/per-directory [FSCTL_SET_COMPRESSION](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_set_compression) as synchronous. A directory establishes a default for future descendants; it does not compress its old contents. The [compression-state contract](https://learn.microsoft.com/en-us/windows/win32/fileio/compression-state) distinguishes that default from actual file state. [GetCompressedFileSizeW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getcompressedfilesizew) supplies allocated-size information separately from logical length. These APIs do not grant a disk quota or reserve space for future nonzero writes.

The entire experiment used one new ordinary C:-volume directory, no links/reparse points, unchanged global settings and a non-elevated token. Data payload totaled **12,582,912 logical bytes**, below the authorized 16 MiB cap; source, results and all files remain private and preserved. Two existing Windows Job/stdin-barrier workers completed in **391 ms** and **141 ms**, respectively, both child0/known cleanup/zero stderr bytes. API/file/stream/mapping handles were closed before result publication.

The private follow-up index binds 18 files / 12,600,099 bytes, including all new probe data, source and results. Its 3,221-byte index SHA-256 is `2260e1cd46d13c5182989aa87974502e6f6f85f9d3513f6fea0334465ed444e7`. Both original preparation evidence and this additional selection are retained separately; no earlier evidence was rewritten.

No sparse-file attribute was set on these files. A read-only 4096-byte mapping of the new compressed zero file returned the expected bytes and closed. A newly created empty child directory and its empty file also inherited format2 without an explicit child compression call. That is a small Windows-file result, not writable QEMU/guest/model mapping compatibility. The zero-file allocation excludes filesystem metadata and does not mean the experiment used zero disk space; volume-wide free-space changes are not attributable solely to its files.

### Path compatibility and remaining requirements

The current environment helper rejects a preexisting AVD root, so manually creating and compressing that very root cannot be an admitted shortcut. A newly created, coordinator-owned compressed **parent** with an absent normal child AVD root is compatible with that source-level absence rule and ordinary nonlinked path enclosure. The tiny child-inheritance observation supports that mechanism without modifying the guest profile. Its exact parent/child paths and compression state still need a future proposal/grant; this research created no AVD container. An alternative hook inside preparation would be a separately reviewed source change, not something this document silently adds.

[QEMU documents](https://www.qemu.org/docs/master/system/images) raw logical length separately from physical allocation. The official [QEMU v9.0 Windows file backend](https://gitlab.com/qemu-project/qemu/-/blob/v9.0.0/block/file-win32.c) opens through CreateFile/ReadFile/WriteFile, conditionally requests overlapped/noncached IO, and uses GetCompressedFileSize for allocated length. That source is **not proven identical to the installed Android emulator**; attempted official Android branch views were unavailable. There is no documented incompatibility established here, but no installed-emulator compatibility result either. The probe did not exercise QEMU's exact flags, aligned/random writes, flush/reopen, QCOW2 overlays or actual guest boot. Microsoft also notes that [compression can increase access time](https://learn.microsoft.com/en-us/windows/win32/fileio/sparse-files), so no speedup, unchanged timing or latency remedy is claimed.

Before any separately admitted VM step: freeze its exact compressed-parent/absent-child paths and final artifact/source hashes; verify inherited attributes on new generated files; bound **physical base + staged model + accepted model + cache/temporary/overlay/evidence growth** per backing; and keep40 GiB on both volumes after every admitted allocation. Random/model/cache writes can consume the saving demonstrated by zeros. If a conservative bound does not fit, report the capacity blocker or obtain a separately reviewed capacity solution; do not reduce reserves or rely on a historical compression ratio. A bounded fresh-VM allocation/IO observation would require its own grant and cannot be inferred from this small probe. No old image, cache, save, model, quarantined target or global compression setting was changed.
