## Authority and lifecycle

The pure closed contract requires an exact reviewed proposal, both scripts,
the genuine B93 handoff, and the current shared-ledger binding in a separate
human-authority record. Strict literal flags authorize fresh preparation and
one boot, while model operations and retirement are false. A nonempty approval
reference is a record of applicable human approval, not authentication against
a local administrator. No script infers approval or creates that record.
The B93 five-file inspection and historical blocked capacity observation never
grant preparation, reservation or execution. No real authority or operation
proposal is created by this implementation packet.

With applicable exact approval, the operator:

1. Verifies the frozen source/helper/Python/build/APK/tool bindings, original
   B88 manifest and four selectors. The original B88 manifest remains authority;
   its separately serialized inspection copy cannot replace it. Existing tool
   metadata is rechecked; only the credential path is carried as metadata, with
   no credential bytes opened, hashed or copied by this bridge.
2. Requires unused output/run/guest paths, the approved current ledger and a
   fresh read-only capacity preview that fits. This does not reserve capacity.
   A create-only attempt directory/record is published before worker dispatch.
   An absent later result never permits another attempt.
3. Assigns one worker to an owned Windows job, binds its kernel identity and
   started record, then releases its stdin barrier. The worker verifies parent,
   request and started joins and creates its own one-use claim before stages.
4. Rechecks the approved ledger and creates a prepare authorization for the
   exact bound proposal. Calls only current public `env.prepare`; its fresh
   locked shared admission, resource, SDK, ownership and parent checks remain.
   The default ledger is unchanged: at most two unretired roots, 64 GiB charged
   budget and 40 GiB reservation for the new guest. Failures remain charged.
5. Verifies the actual prepared/result/config/initial-SD bindings through
   `env.verify_prepared(initial=True)`, exact fresh prepared ledger entry, known
   preparation cleanup and no boot claim. A terminal file or returned object
   alone is insufficient. A fresh entry must have no recovery history.
6. Uses `env.plan_run` and a new exact run authorization, builds the standard
   SDK16 admission, and revalidates the current profile/build and source closure.
   It snapshots the prepared ledger and requires the same bytes through final
   input publication. Admission precedes the create-only activation input.
7. Calls the existing Knowledge activation, which owns the private server,
   guest, four-method controller, cancellation and cleanup. Acceptance requires
   joined stored activation/runtime results and the actual closed ledger entry
   with matching run proposal/admission and known storage closure. Feature
   acceptance stays false; a host fixture cannot qualify Android journeys.

The authority's pre-preparation ledger snapshot is checked before preparation;
the ledger necessarily changes during guarded preparation. That old snapshot
is never reused as post-preparation admission. Partial authorizations, inputs,
claims and failures stay in place and cause refusal on reuse. No repair or
automatic retry is supplied.
