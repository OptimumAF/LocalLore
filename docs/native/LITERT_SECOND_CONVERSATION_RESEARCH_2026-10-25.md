# LiteRT-LM second-conversation source investigation — 2026-10-25

Refs #9 (M05.05 prerequisite; M01.05 supporting). **Research only; real-backend acceptance remains pending.** The pinned API supports sequential fresh conversations on one engine. It also performs fresh LLGuidance tokenizer setup for every response-format-enabled conversation. That is a concrete cost to investigate, not an established cause of the latest failure. The current director, repair, and narrator requests all require structured output; disabling narrator constraints is not an applicable remedy.

This report reads repository sources at `daad3b598a43b0fe862d894c5633a7ce77892ead` and official upstream sources at LiteRT-LM **0.18.1 / `bda624851d74be34d4e1f7fac1fc4155939539c7`**. Claim: #9 comment 6395370165. No SDK, model, device, emulator, build, dependency installation, or runtime operation was performed. No private model, image, cache, generated text, or save contents were read.

## Observed boundary, supplied by the coordinator

The fresh C experiment recorded initialize returned once; 24 message-body entries/exits; one done-body exit, settled drain branch, and known conversation-close result. Conversation creation was entered twice and returned once; no second send was recorded. Engine close and uncertainty-notification counts were zero at that snapshot. PLAY failed with `LocalInferenceUncertain` after 80.392 seconds, without Prepared, commit, or reopen. All original host/VM handles subsequently reached terminal closure.

These counters locate an unfinished second creation operation, not its native substep, role, exception, scheduling state, or cause. Role two might be a director repair or narrator. Callback exits exclude hidden JNI epilogues; zero uncertainty notifications is not a health or reclamation proof. This research did not independently re-audit the private run.

## Pinned creation and release contracts

* Kotlin [`Engine.createConversation`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/kotlin/java/com/google/ai/edge/litertlm/Engine.kt#L111-L160) holds the engine monitor, checks its handle, calls JNI, and constructs a separate Conversation. `isInitialized()` tests handle presence; it is not an idle-task status.
* Native [`Conversation::Create`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/conversation/conversation.cc#L390-L465) creates a session, model-data processor, and optional constraint provider. Preface prefill is conditional. Current app configuration leaves prefill disabled and supplies no initial messages/tools; there is no source basis for assuming an intentional second prompt prefill here.
* [`EngineAdvancedImpl::CreateSession`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/core/engine_advanced_impl.cc#L122-L165) registers a fresh session. The resource manager's [`CreateContextHandler`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/framework/resource_management/resource_manager.cc#L520-L590) takes the executor mutex around context creation. Thus context creation/locking and later processor/constraint setup are separate candidates inside the observed boundary; no stack observation selects one.
* Kotlin [`Conversation.close`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/kotlin/java/com/google/ai/edge/litertlm/Conversation.kt#L708-L714) marks its handle dead before native deletion. Native [`SessionAdvanced` destruction](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/core/session_advanced.cc#L443-L456) waits for session work, ignores that wait's error status, and releases the session. Consequently, returned close is meaningful but exposes no structured wait/release status.
* The threaded manager runs the terminal callback before updating terminal task state; its session wait requires the active-task set to empty. It removes the released session and resets the current executor handler when no sessions remain. These details weaken a simple “onDone returned, therefore native work is finished” argument, while making an actually returned native close stronger than the callback trace alone. See [`FinishTask`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/framework/resource_management/threaded_execution_manager.cc#L484-L514), [`WaitUntilSessionDone`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/framework/resource_management/threaded_execution_manager.cc#L771-L791), and [`ReleaseSession`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/framework/resource_management/threaded_execution_manager.cc#L184-L211).

The pinned native [engine tests](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/core/engine_advanced_impl_test.cc#L156-L216) explicitly destroy the first session, create another on the same engine/cache, and generate again. This is upstream sequential-session coverage, not qualification of our model/device or several simultaneously live preloaded conversations.

## Repeated structured-output initialization

The documented [`enableResponseFormat`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/kotlin/java/com/google/ai/edge/litertlm/Config.kt#L228-L264) initializes LLGuidance. JNI [sets a constraint-provider configuration](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/kotlin/java/com/google/ai/edge/litertlm/jni/litertlm.cc#L1021-L1024) for that flag. The [provider factory](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/components/constrained_decoding/constraint_provider_factory.cc#L27-L55) creates a provider per call. [`LlgConstraintProvider::Create`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/components/constrained_decoding/llg_constraint_provider.cc#L56-L128) gathers vocabulary bytes and invokes `llg_new_tokenizer`; destruction frees that tokenizer.

There is no public Kotlin parameter for sharing this tokenizer across fresh conversations. The provider [owns its tokenizer and backing vectors](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/runtime/components/constrained_decoding/llg_constraint_provider.h#L31-L53). Reusing an entire Conversation would also reuse its interaction state and is not a substitute for tokenizer sharing or fresh-role isolation.

In official [issue #3721](https://github.com/google-ai-edge/LiteRT-LM/issues/3721), a maintainer confirmed reproducing tokenizer-initialization overhead on September 24. At this review the issue remained open with no linked fix; its reported device timings are not LocalLore measurements. The separately reported special-token correctness problem also means schema configuration alone is not proof of complete constrained-output correctness.

## What the earlier Android spike established

Repository [warm results](../runtime/android/WARM_RESULTS_2026-10-22.json) and [verification](../runtime/android/WARM_VERIFICATION_2026-10-22.md) retain seven requests/twelve attempted roles: five committed turns each used one engine and two fresh closed conversations; two requests cancelled. This is actual earlier reuse evidence on 0.18.1, with its own conditions and limitations.

`SpikeInstrumentation.WarmModel` and `CacheSdkModel` enabled response formatting only when their request carried a schema, rendered a template before sending, queried benchmark information after terminal generation, and returned through a host validation/request exchange before creating the next role. The old warm narrator was plain text. None of those intervening calls/delays is documented as a synchronization fence. The later [explicit-cache control](../runtime/android/CACHE_SDK_CONTROL_DEVICE_2026-10-23.md) completed only a director and was rejected as Agency; it did not exercise narrator reuse.

Current `LocalInferenceRequest.schemaJson` is mandatory. `play.rs::role_request` constructs `Input::Structured`; narrator uses `narration_schema(approved.events())`, including text, event IDs and speaker policy. The external inference packet retains that schema and the worker always passes `ResponseFormat.json(request.schemaJson)`. An initial suggestion to conditionally disable the flag was withdrawn after checking these current contracts. The old plain-narrator topology cannot stand in for the current two-structured-role gate.

## Minimal next options and discriminating checks

1. **Keep constraints and expose the missing distinction.** Record only a closed role/attempt ordinal and bounded monotonic elapsed values around creation, plus returned/failed category. A repair must remain distinguishable from a narrator without retaining prompts, schemas, output, paths, or arbitrary exception text. This would select the affected operation; it would not by itself repair it.
2. **Evaluate measured pre-creation as an explicit setup phase.** The public API can create fresh Conversation objects, but has no tokenizer preload/cache API. A separately reviewed experiment could prepare distinct structured director/repair/narrator slots before starting the unchanged turn deadline. It must qualify simultaneous-live-session support, fresh histories, memory, cancellation, unused-slot closure, and cold end-to-end time. Unsupported creation must stop, not reuse role history or silently drop constraints. This topology is currently untested.
3. **If cost is confirmed, prefer a narrow upstream tokenizer-cache change.** Cache tokenizer-only construction with explicit engine/config lifetime and thread-safety tests; keep each conversation's mutable constraint/history/KV ownership independent. Native ownership currently frees the tokenizer per provider, so merely sharing its pointer is unsafe. This requires a separately pinned, built and audited runtime change; it is not available through an existing public Kotlin flag.

Before real execution, deterministic seams should test director→narrator and director→repair→narrator ordering, required schemas on every send, no next role until prior close result, no accepted commit on a failed/unfinished create, and retained ownership on cancellation. Real qualification must still observe both structured generations and canonical commit/reopen under the existing 60-second turn/5-second cleanup limits. No arbitrary delay, timeout increase, forced close, or poison reset is recommended.

## Public status and current upstream checks

JNI [calls Java onDone before its terminal-reference cleanup/detach](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/kotlin/java/com/google/ai/edge/litertlm/jni/litertlm.cc#L1171-L1217). Kotlin async errors map native cancellation to `CancellationException`, and other status details into [`LiteRtLmJniException`](https://github.com/google-ai-edge/LiteRT-LM/blob/bda624851d74be34d4e1f7fac1fc4155939539c7/kotlin/java/com/google/ai/edge/litertlm/LiteRtLmJniException.kt), which has no typed status-code property. Safe reporting can retain fixed operation/category booleans; it should not parse or emit that message. `isAlive`, token counts, and benchmark information are not idle/resource-release proofs. Switching to synchronous send introduces different blocking/cancellation behavior and is not established as a fix.

The [official release list](https://github.com/google-ai-edge/LiteRT-LM/releases/tag/v0.18.1), checked October 25, still identifies 0.18.1 as latest stable; its noted fix concerns EmbeddingGemma 2 source-build ABI compatibility. No verified newer stable fix was found for this boundary. [Issue #3266](https://github.com/google-ai-edge/LiteRT-LM/issues/3266) reports missing terminal callbacks on older Android versions, unlike this run's done/close observations. [Issue #3771](https://github.com/google-ai-edge/LiteRT-LM/issues/3771) concerns destruction during prefill, also not this observed sequence. [Issue #2028](https://github.com/google-ai-edge/LiteRT-LM/issues/2028) was closed for inactivity, not a demonstrated fix. These reports do not diagnose LocalLore or justify a blind dependency change.

Only source inspection and documentation diff checks were performed here. M05.05/M01.05 acceptance and a working real receipt-backed two-role backend remain pending.
