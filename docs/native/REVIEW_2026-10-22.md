## Concrete findings and corrections

1. **Count retained resources when admitting new sessions.** The first draft
   admitted sessions using registry-map length. Destroy removes a handle from
   that map before a running invocation drops its retained `Arc<Session>`.
   Repeated create/run/destroy could therefore exceed the advertised retained
   session cap. The corrected code checks the lifetime session counter while
   holding the registry lock. Begin also reserves against a global operation
   cap under that lock, bounding cancelled operations still held by workers.
   Closed handles fail without pointer dereferences; actual worker/session
   release occurs after the running call unwinds normally.
2. **Allocate all public IDs with the same checked range.** Create originally
   checked increment/positive `i64` capacity while begin used unchecked `+=1`.
   Both now use checked addition and reject IDs beyond `i64::MAX`, preserving
   the Java `Long` representation and avoiding overflow/poisoned-registry
   failure at exhaustion. This boundary cannot practically iterate to ID
   exhaustion; the checked source was inspected, not falsely tested at that
   cardinality.
3. **Do not claim rollback after an uncertain commit transport failure.** The
   initial generic ViewModel exception notice said “Nothing changed” even if
   Rust had committed before a reply-decoding failure. The corrected ViewModel
   tracks the commit phase, reports that it cannot confirm the outcome, blocks
   further submission/mode changes, and requires explicit reset of this
   in-memory demo. The coordinator added
   `unknownCommitFailureRequiresResetAndDoesNotClaimRollback`, simulating a
   commit callback which throws after entering commit. This is source-reviewed;
   its actual JVM result is the coordinator's evidence. Durable restoration
   instead of demo reset remains part of the persistence work.

The three corrections were re-inspected in coordinator source. No unresolved
blocking source defect was identified in the reviewed bounded fake-provider
slice. That statement is not a security certification or device/model approval.

## Boundary and lifetime observations

There is one named JNI method, `(J[B)[B`, implemented as `extern "system"`.
The Kotlin object calls `System.loadLibrary` before use. Java owns its arrays;
Rust checks array length before copying, never retains JNI environments/references,
creates no JVM/native worker thread, and returns a fresh bounded array.
The input may be null so a real JNI regression can exercise that rejection.
Raw native memory pointers, class caches, callbacks and pinned-array lifetimes
are absent. See [official-source constraints](SOURCES_2026-10-22.md), including
why `jni = =0.21.1` is a deliberate older API pin and the limits of panic recovery.

Rust owns each real engine and one active operation. Preparation runs the actual
Rust fake provider/engine pipeline on a cloned engine. The registry-owned engine
is unchanged until explicit commit. Commit/cancel serialize under the same
session/operation locks; accepted duplicate commits return the recorded reply.
Generation holds neither engine nor global-registry locks while polling. Cancel
signals a one-way token; destroy also removes the public handle. Retained engine,
operation and worker populations are instrumented separately.

Kotlin enforces main-thread control ownership and uses `Dispatchers.IO` for the
single blocking native run. The suspending call returns only a prepared handle.
The ViewModel checks generation/revision before its non-suspending commit and
StateFlow publication. Cancellation discarded by `withContext` signals the
captured operation in `finally`; old cleanup cannot target the replacement
session. Clear closes the session, reset closes/recreates it, and lifecycle stop
cancels pending work. A native call which is already executing remains alive
until it observes cancellation and returns; claiming immediate thread termination
would be inaccurate.
