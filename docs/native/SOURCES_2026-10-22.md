# Native boundary sources — 2026-10-22

Scope: M03.03, ticket [#7](https://github.com/OptimumAF/LocalLore/issues/7).
These are official-source compatibility and ownership notes, not model/runtime
selection, a security certification, or evidence of device execution.

## JNI dependency choice

The native adapter pins `jni = "=0.21.1"` with default features disabled. This is
an intentional bounded API choice, not a claim that 0.21.1 is current latest.
On 2026-10-22 [latest upstream documentation](https://docs.rs/jni/latest/jni/)
resolved to 0.22.4, whose `EnvUnowned` / `Env` native-entry API differs materially.
For one byte-array call, the older API permits a small explicit wrapper whose
allocations, JNI references, errors and unwind barrier can be reviewed together.
Upgrade assessment remains required before expanding JNI functionality or
shipping a release. A later version existing alone does not establish a known
vulnerability in the bounded operations used here; this review is not a full
vulnerability audit.

Verified [published 0.21.1 documentation](https://docs.rs/jni/0.21.1/jni/) and
[tagged source manifest](https://github.com/jni-rs/jni-rs/blob/v0.21.1/Cargo.toml).
The package uses edition 2018, declares no explicit minimum Rust version, and
has an empty default-feature set. The optional `invocation` feature enables
JVM-location/loading dependencies; LocalLore does not enable it or start a JVM.
Pinned Rust 1.93.1 compilation and actual Android linking are separate recorded
checks, not inferred from the missing MSRV field.

The [crates.io version record](https://crates.io/api/v1/crates/jni/0.21.1)
reports package SHA-256
`1a87aa2bb7d2af34197c04845522473242e1aa17c12f4935d5856491a7fb8c97`.
Tagged Cargo metadata declares `MIT/Apache-2.0`; both the
[MIT license](https://github.com/jni-rs/jni-rs/blob/v0.21.1/LICENSE-MIT) and

The [tagged JNI wrapper source](https://github.com/jni-rs/jni-rs/blob/v0.21.1/src/wrapper/jnienv.rs)
implements `convert_byte_array` by allocating the Java array length and copying
with `GetByteArrayRegion`. The caller must enforce the input limit first.
`byte_array_from_slice` casts its slice length to `i32`, so enforce the response
bound before invoking it. No pinned array elements/direct buffers are necessary.

## Ownership and failure constraints

[Android JNI guidance](https://developer.android.com/training/articles/perf-jni)
requires `JNIEnv` to remain on its calling thread and local references to remain
within their native invocation. It describes pending-exception restrictions,
per-call local cleanup, emulator CheckJNI, library loading, and both native-method
registration and name-based discovery. General guidance prefers `RegisterNatives`
for early mismatch detection. One explicitly exported, exercised method uses the
supported discovery path here; no `FastNative` / `CriticalNative` optimization,
Java callback, native-created thread or retained Java reference is needed.

Use Java-owned input/output arrays and copy into bounded Rust-owned values;
return arrays created in the current JNI invocation. The native registry owns
Rust engines and cancellation tokens, keyed by opaque monotonically allocated
IDs rather than raw pointer casts. A background caller owns one run invocation;
cancel/destroy invalidate its token, and release happens after that invocation
returns. A handle absent from the registry is an error, never a dereference.

The [Rust FFI guide](https://doc.rust-lang.org/nomicon/ffi.html) describes the
need for correct ABI/signatures and an ownership-safe wrapper.
[`catch_unwind`](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html) catches
unwinding panics only; aborts and allocation exhaustion are not recoverable by
that mechanism. Keep an explicit unwind barrier around Rust dispatch and avoid
panic payload/error text in player-facing diagnostics. Ordinary failures use
bounded typed error categories. An existing JVM exception must remain pending;
no additional JNI allocation or throwing should occur while it is pending.

The UI-side commit is deliberately short and non-suspending: generation prepares
a draft on a clone; only explicit commit changes the registry-owned engine.
Cancellation before commit leaves canonical state unchanged. Once commit wins,
publish its accepted result on the same UI owner before another cancel/reset
callback executes. A resource counter reaching zero after a test proves only the
instrumented lifetime population, not the absence of every possible native leak.

Exact build/NDK compatibility and packaging checks are recorded in sibling
BUILD documentation by the independent build contributor. Actual host/emulator
verification belongs in the coordinator's dated verification report.
