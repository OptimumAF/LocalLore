## Busy fixture: mechanism correction required

The initial proposal was an Android `SQLiteDatabase` writer transaction against the synthetic database already owned by Rust. A dedicated thread would preserve Android transaction ownership, but it would not solve the separate-library locking problem: the Android platform SQLite and Rust's bundled SQLite are distinct library copies in the same process.

SQLite's [official corruption guidance, sections 2.2–2.3](https://www.sqlite.org/howtocorrupt.html#multiple_copies_of_sqlite_linked_into_the_same_application), explains that Unix advisory locks are process-owned and that separate library copies have independent internal lock bookkeeping. Closing a descriptor from one copy can invalidate another copy's locks. Consequently, a same-process platform writer cannot be assumed to produce a valid Busy conflict against the bundled engine; it can also undermine the locking guarantee being tested. This concrete mechanism issue was sent to the coordinator and author before any execution. The author confirmed the candidate remained unbuilt/unrun and paused that mechanism.

A valid replacement needs either a distinct owned holder process using the same filesystem locking protocol, or a transaction held through the same bundled SQLite implementation with appropriate shared bookkeeping. The current frozen engine wire does not expose a raw transaction operation. A test-only process/service or native helper would need explicit file ownership and a narrow reviewed interface; do not silently add a production transaction/fault command. A separate process must open its own connection rather than inherit an open SQLite connection across a fork. No fake envelope can stand in for actual Rust Busy evidence.

## Android transaction and configuration constraints

The public [SQLiteDatabase API](https://developer.android.com/reference/android/database/sqlite/SQLiteDatabase) defines `beginTransactionNonExclusive()` as IMMEDIATE. Pair it with `endTransaction()` without marking success when the holder makes no data change. Android's [API-35 SQLiteSession source](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-15.0.0_r1/core/java/android/database/sqlite/SQLiteSession.java) makes transaction state thread-bound: open/begin/query/end/close should remain on one owned worker thread. Suspend dispatcher switching alone does not guarantee the same thread.

Use only an existing, exact synthetic path, no CREATE flag or SQLiteOpenHelper migration. `NO_LOCALIZED_COLLATORS` matters: the [Android-15 connection source](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-15.0.0_r1/core/java/android/database/sqlite/SQLiteConnection.java) otherwise creates/updates Android locale metadata, which would violate the engine's verified schema. Opening also configures journal behavior. The [configuration source](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-15.0.0_r1/core/java/android/database/sqlite/SQLiteDatabaseConfiguration.java) can select a platform default, and SQLiteDatabase can add compatibility-WAL flags. Absence of an explicit WAL flag is not proof of unchanged journal mode.

For an API-35 holder, [OpenParams.Builder.setJournalMode](https://developer.android.com/reference/android/database/sqlite/SQLiteDatabase.OpenParams.Builder#setJournalMode(java.lang.String)) permits explicit mode selection (API 28+); unspecified mode can vary by manufacturer. Preserve the verified existing mode rather than change it. Compare schema, application/user versions and journal mode before/after opening/closing the holder. No locale table, gameplay row, journal policy or schema mutation belongs in a contention fixture.

SQLite's [transaction documentation](https://www.sqlite.org/lang_transaction.html) permits only one writer: IMMEDIATE requests the write transaction immediately. In rollback mode a RESERVED writer can coexist with readers, unlike EXCLUSIVE; this lets the test distinguish failed write admission from unreadable snapshots. The actual selected mode and Rust result must be observed, not inferred from a successful holder API call. The store configures a 250-ms busy timeout and maps Busy/Locked errors to the fixed Busy category. Timeout duration is not a performance claim.

## Actual Full through Compose: missing prerequisite

The repository's native pressure tests apply `max_page_count` on the actual Store connection. An Android-side pragma does not set a persistent file quota for a different Rust owner. Source inspection of the pinned `libsqlite3-sys 0.38.2` amalgamation identifies SQLite `3.53.2`: `OP_MaxPgcnt` addresses the executing connection's Btree/Pager; `sqlite3PagerMaxPageCount` sets the Pager's in-memory `mxPgno`; new Pager creation initializes that field from `SQLITE_MAX_PAGE_COUNT`. There is no database-header quota written by this path. This agrees with the [official Pager implementation](https://sqlite.org/src/doc/trunk/src/pager.c) and the [pragma's documented page-limit semantics](https://www.sqlite.org/pragma.html#pragma_max_page_count). Shared-cache cases do not bridge these two separately linked libraries.

No safe actual-Full-through-Compose mechanism was identified under the current frozen wire and prohibition on production fault hooks, global disk filling, root or emulator setting changes. Permission failures, read-only files, invalid paths and I/O failures are different errors; injected Full replies remain protocol tests. None should be relabeled SQLITE_FULL.

The missing prerequisite is a separately authorized and reviewed bounded capacity sandbox (for example, a genuinely isolated filesystem/quota environment) or a strictly test-only owner-connection capacity fixture with honest native-binary scope. Neither currently exists in the frozen production interface. Keep actual Full-through-Compose open; retain the separate native page-cap evidence and the accepted injected-frame Compose evidence without combining them into an unrun end-to-end result.
