## Official contracts and concrete corrections

[`Process.getStartElapsedRealtime()`](https://developer.android.com/reference/android/os/Process#getStartElapsedRealtime()) is available from API24 and gives the current process's start in the elapsed-realtime time base, before app code runs. It is not an epoch timestamp or a start time for an arbitrary other PID. Store it with current PID/UID and a unique run identity before entering diagnostic work.

[`ActivityManager`](https://developer.android.com/reference/android/app/ActivityManager#getHistoricalProcessExitReasons(java.lang.String,%20int,%20int)) adds historical exit queries and process summaries at API30. Query the exact own package, saved PID and a positive bounded result count. Zero PID broadens matching, zero count removes the requested count bound, null package includes the caller UID's packages, and external bound-service processes can appear. The history is a finite ring, so absence is not proof that no death occurred. Tagged [Android15 tracker source](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/services/core/java/com/android/server/am/AppExitInfoTracker.java) also stores records by PID; later reuse can replace an older entry.

The initial suggested 256-byte process summary exceeds the official limit: **maximum 128 bytes**. This was reported immediately. Calls can be throttled and throw; the summary is optional diagnostic data, never UI restoration or canonical state. Keep it small and fixed, containing no player text, generated output, model path or other sensitive content. Record summary failure separately while retaining the durable journal.

[`ApplicationExitInfo`](https://developer.android.com/reference/android/app/ApplicationExitInfo) supplies epoch-millisecond death timestamps, PID, package UID, process name and nullable process summary, but no process-start elapsed time. Persisted start identity must therefore be carried in the journal and summary. Wall time can change while elapsed time advances; they cannot be compared directly. Paired epoch/elapsed samples support limited window checks, not an exact conversion across clock changes or reboot. Reason/status report OS observations; a signal number does not identify watchdog, memory pressure or a responsible library. Memory sizes are last samples, not guaranteed crash-time or peak measurements.

## Diagnostic boundaries reviewed

Use a create-new private no-backup run directory and a small, bounded fixed-enum journal. Bind its owner, version, run nonce, PID/UID, process-start elapsed time, strictly increasing sequence, fixed phase and paired clocks. Persist and sync an entry before each potentially failing stage; if required journal persistence fails, do not enter SDK work. A durable `entered` phase establishes the last recorded boundary, not successful completion or crash causation. Detect torn/truncated records without inventing missing completion. No fresh reader may overwrite or adopt an older run.

An optional summary can identify the run and process instance within 128 bytes. Exact saved PID, package UID, process name and summary identity can support an instance match. Missing, mismatched or malformed summaries must remain unknown; picking the newest PID/time match cannot establish identity. Keep original probe result, journal outcome and OS exit observation separate. Query failures must not erase the original error or authorize further work with unknown ownership.

There is a further reuse case: one live PID/start can execute runA and then runB. If B's summary update fails, a later exit may retain A's summary. Even a matching nonce then cannot establish that A's completed SDK attempt caused that death. Either require and verify a fresh process per attempt, or keep process-instance matching separate from run-completion/window validation and causal claims.

Reviewed host tests cover wrong PID/run/start/UID/name and null summaries, strict ambiguous-observation counters, journal wall-clock jumps/elapsed reset, partial writes, sequence/identity/type violations, sticky close uncertainty and checkpoint failure before work. Actual device qualification is narrower: deliberate process death and one fresh read. It does not inject clock changes, PID reuse, summary throttling, filesystem failure or an unkillable SDK worker on Android.
