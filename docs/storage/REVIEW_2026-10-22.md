# Independent M04.01 storage review

Scope: versioned SQLite schema/migration and validated seed storage, stacked on
the unmerged M03.03 ownership follow-up #35. This review grants no owner
acceptance and does not claim durable accepted turns, outcome reducers, crash
recovery, real inference or a supported device profile.

The reviewer used separate `review/m04-storage` / `LocalLore-storage-review`,
starting at `e5d1c5b`. Earlier runtime and native reviews stayed in their own
worktree. Exclusive reviewer files are
`crates/locallore-storage/tests/adversarial.rs` and this document. The coordinator
owns the schema, storage API, dependencies and fixes. No emulator, model,
GitHub mutation or production-source edit was performed by this reviewer.

## Concrete findings

### User objects hidden by a wildcard

The original schema query used `name NOT LIKE 'sqlite_%'`. The underscore is a
SQL wildcard, so the allowed user table `sqliteXprivate` disappeared from
inspection. An in-memory SQL probe first confirmed the filter behavior. Actual
Store tests then reproduced both failures against coordinator commits
`d20dafc` / `74468d5`:

- A nonempty version-zero database was adopted and migrated.
- A version-one database with the extra table passed schema verification.

The first 12-test run had 10 passes and those two failures. The coordinator's
`7bb5d12` replaces the pattern with a literal-prefix GLOB check. Both tests now
require rejection, unchanged source bytes and, for the foreign database, no
backup creation.

### Stale identity during migration lock acquisition

Store initially read application/schema identity before acquiring its migration
write lock. Another writer could promote an otherwise empty version-zero
database to future version 2 while Store waited, after which Store initialized
version 1 using the stale identity. A controlled host regression reproduced
this as `concurrently promoted future database was adopted`.

The coordinator now reads/classifies identity again under BEGIN IMMEDIATE,
before backup creation or DDL. The regression expects FutureVersion, no new
backup and version 2 unchanged. It holds a raw writer transaction before
starting Store, then commits after an 80 ms scheduling interval. That interval
exercised the bad ordering on this host; it is not a deterministic scheduler
hook. A delayed Store thread may instead take the earlier future-version
refusal path. The refusal/no-overwrite postcondition applies in either ordering.

### Windows backup flush handle

A small independent Rust 1.93.1/Windows probe observed read-only
`File::open(...).sync_all()` fail with PermissionDenied/OS error 5; a writable
handle succeeded. The coordinator corrected the backup's final flush to use
writable OpenOptions before the implementation commits reviewed here. The
actual migration/backup/WAL tests pass with that handle. This is finite host
evidence, not a power-loss or filesystem durability guarantee.

## Actual checks

The reviewer cherry-picked coordinator implementation commits `d20dafc`,
`74468d5` and correction `7bb5d12` for compilation, without editing their files.
On Windows x86_64 / Rust 1.93.1, with locked/offline dependencies:

| Command | Observed result |
|---|---|
| `cargo test -p locallore-storage --test adversarial --locked --offline` after correction | 13 passed before the Busy case was added |
| `cargo test -p locallore-storage --locked --offline` final suite | 14 independent integration tests and 2 coordinator unit tests passed; zero failures |
| `cargo fmt --all --check` | Passed |
| `cargo clippy -p locallore-storage --all-targets --locked --offline -- -D warnings` | Passed |
| `git diff --check` | Passed |

One initial test compilation used the wrong generic argument ordering for
rusqlite's pragma helper. The test call was corrected before the executable
baseline results above; that compiler failure was not a storage failure.

The fourteen independent tests cover:

- New/reopened/second owning connections, FK enabled and two stories sharing
  titles and local actor/item identifiers without mixing their seeds.
- Existing-empty migration backup requirement, unchanged refused source,
  readable/integrity-checked original version-zero safety backup.
- Foreign/future/negative versions, ordinary schema changes and the hidden-name
  regressions, with no mutation or spurious backup on refusal.
- Existing backup files, an empty existing file, the source itself and an
  existing directory with a sentinel; none is overwritten.
- Invalid seed/title and duplicate-story atomicity, followed by successful use
  of the previously rejected story ID.
- A real committed WAL update while the writer stays open and the main database
  bytes remain unchanged. SQLite backup includes the update, reopens normally
  and retains FK enforcement. Copying the stale main file would fail this case.
- Cross-story entity, cross-branch, cross-story turn and observer references
  rejected specifically by composite foreign keys. Equal turn IDs/sequences
  in independent stories succeed. Final foreign_key_check is empty.
- A corrupt stored seed rejected as Integrity, without leaking a synthetic
  private content/path canary through Display or Debug error text.
- Another connection holding BEGIN IMMEDIATE causes create_story to return Busy
  without inserting a second story or altering the original seed; releasing the
  writer allows the same request to succeed. The test has a generous three-second
  host return bound, not a database/phone performance target.

Raw rusqlite connections appear only in these tests to construct deliberate
invalid databases, retained WAL state, writer contention and SQL constraint
probes. Minimal `{}` event/turn payloads in those probes test relational keys;
they do not claim engine validation or usable accepted history. Production
Store exposes no connection or arbitrary SQL executor. Source inspection also
confirms configure is called for owning, backup and reference connections.
The two coordinator unit tests directly check FK/trusted-schema/extension
configuration and injected DDL rollback of schema/data/version changes.

## Limits and handoff

The public storage slice saves/loads a validated root seed; it does not yet
persist accepted gameplay turns or replay projections. Branch/turn/event tables
are constrained storage shapes, not completion of M04.02–M04.06. No hostile
archive import, arbitrary SQL capability, concurrent gameplay writer, disk-full
fault matrix, process/power-loss recovery or filesystem adversary qualification
is established. Consistent backup tests do not prove recovery from every OS or
hardware failure. Symlink-specific tests were not run on this Windows host.

No remaining concrete defect was observed in the corrected, exercised storage
slice. Final integrated host checks, Android ABI builds/model-free emulator
execution, dependency/source evidence, ticket reconciliation and PR handoff
remain coordinator responsibilities. M04.01 stays unchecked until its full
evidence and owner acceptance are recorded; #35 remains a separate prerequisite.
