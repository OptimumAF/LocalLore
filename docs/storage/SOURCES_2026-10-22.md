# Bundled SQLite dependency and Android build verification

M04.01, independently reviewed before the coordinator introduced the dependency.
The exact source/artifact hashes, registry versions, license declarations and
license-file hashes are in [DEPENDENCY_SOURCES.json](DEPENDENCY_SOURCES.json).
The coordinator owns schema/migration decisions and emulator execution. This
report covers dependency provenance, an actual host smoke and two cross-builds.

## Dependency decision and compatibility

The official registry and [release documentation](https://docs.rs/crate/rusqlite/0.40.2)
both identified `rusqlite 0.40.2` as current during this check. Its registry
package and `libsqlite3-sys 0.38.2` identify upstream revision
`e88f112bef7899234a497baed5cc3c3d553deeb8`. Both downloaded crate archives were
SHA-256 verified against the registry API before use. Seven reviewed files,
including the two original manifests, build script, license, README, SQLite
header and amalgamation, were also byte-compared with that exact official
upstream revision. Normalized registry manifests are distinguished from their
`Cargo.toml.orig` inputs in the evidence manifest.

Selected configuration:

```toml
rusqlite = { version = "=0.40.2", default-features = false, features = ["bundled", "backup"] }
```

The coordinator's Cargo.lock pins the native wrapper and all resolved
transitives. The bundled source is SQLite **3.53.2**, version number `3053002`,
source ID `2026-06-03 19:12:13 d6e03d8c777cfa2d35e3b60d8ec3e0187f3e9f99d8e2ee9cac695fd6fcdf1a24`.
This is compiled into the Rust owner; it is not Android's system SQLite.
`backup` exposes the existing online backup API without an extra native
dependency. Default cache/Wasm features, SQLCipher, OpenSSL, extension API,
runtime bindgen and broad `bundled-full` features are not selected. Pregenerated
bundled bindings avoid a new libclang/bindgen provisioning requirement.

The [upstream MSRV policy](https://github.com/rusqlite/rusqlite/blob/e88f112bef7899234a497baed5cc3c3d553deeb8/README.md#minimum-supported-rust-version-msrv)
is the latest stable Rust at release, rather than a numeric minimum; neither
published wrapper manifest declares `rust-version`. Compatibility with the
repository's **Rust 1.93.1** was established by actually compiling and running
an isolated in-memory query first, then compiling/running the real storage
example and cross-building both Android ABIs. This is evidence for these
versions/features, not a promise about future rusqlite releases.

The [native build source](https://github.com/rusqlite/rusqlite/blob/e88f112bef7899234a497baed5cc3c3d553deeb8/libsqlite3-sys/build.rs)
uses `cc`, sets `SQLITE_THREADSAFE=1`, `SQLITE_DEFAULT_FOREIGN_KEYS=1` and, on
Android, `SQLITE_TEMP_STORE=3`. The Store still enables and verifies foreign
keys on each owned connection; a compile-time default is insufficient.
The bundled native build also defines `SQLITE_ENABLE_LOAD_EXTENSION=1`.
Disabling the Rust `load_extension` feature does **not** remove that native
code. Connection ownership stays private, no untrusted SQL is exposed, and
the coordinator's connection test verifies that loading remains unauthorized.
No claim of extension code being compiled out is made.

## Actual storage smoke

The example uses only the original repository fixture, the frozen Store API
and a newly created directory. It refuses a pre-existing directory, retains
no model data and prints only fixed enum/numeric/boolean JSON. It creates two
stories with the same display names/entity/item IDs but different scoped
potion quantities, closes and reopens the database, checks exact seed equality
per scope, makes/reopens a consistent backup, and checks existing-destination
refusal. It confirms schema 1, foreign keys enabled and bundled SQLite version.
It does not execute or persist a gameplay turn, reducer or model response.

Run from the repository root with a new directory name:

```powershell
cargo +1.93.1 run --locked --offline -p locallore-storage --example storage_smoke -- --directory target/storage-smoke-example
```

Actual final host invocation, using coordinator source through `7bb5d12`,
exited 0 and returned `completed`, `stories_reopened=2`,
`stories_backed_up=2`, `same_entity_ids_isolated=true`,
`existing_backup_refused=true`, `foreign_keys=true`, `schema_version=1`,
`sqlite_version=[3,53,2]`. The initial example compile caught an unnecessary
direct Serde derive; it was replaced by fixed error-code mapping, without
adding a dependency.
Actual direct invocations with missing arguments and a pre-existing directory
each exited 1 with the expected fixed `arguments`/`directory` JSON error and
zero stderr bytes. `cargo +1.93.1 clippy --locked --offline -p
locallore-storage --all-targets -- -D warnings`, workspace format checking,
Python syntax compilation and `git diff --check` passed.

## Actual Android cross-builds

Existing tools: Windows x64, Python 3.9.12, Rust 1.93.1,
NDK 29.0.14206865/r29, Clang 21.0.0. The recipe targets API 26, matching the
existing Android harness. It uses the already installed Rust targets and NDK;
it does not install an SDK, fetch dependencies, use a model or invoke ADB.
The [official NDK compiler guidance](https://developer.android.com/ndk/guides/other_build_systems)
and [Rust Android target documentation](https://doc.rust-lang.org/rustc/platform-support/android.html)
were checked before compiling.

```powershell
python scripts/storage_android_smoke.py --sdk "$env:LOCALAPPDATA/Android/Sdk"
```

The command runs Cargo `--locked --offline --release` sequentially for
`x86_64-linux-android` and `aarch64-linux-android`. The existing Rust response
adapter preserves workspace apostrophes; encoded Rust flags keep each SDK
path as one linker argument. Native C compilation explicitly uses target
Clang/llvm-ar, target API and sysroot. An initial quoted CFLAGS attempt failed
because `cc` splits flags on spaces by default; the tested recipe now sets
its documented `CC_SHELL_ESCAPED_FLAGS=1` and quotes the POSIX-form sysroot.
No source patch or new build dependency was needed.

Both final commands exited 0 against coordinator fixes through `7bb5d12`:

| ABI | Bytes | SHA-256 |
|---|---:|---|
| x86_64 | 3394256 | `5fae54a7ffaa415654f8e051285ccba650185e995cea6b77044f1adde6188b32` |
| arm64-v8a | 3429952 | `5788ef7602ccd6a8da55ad984f6af49c9b1ced6b912e4b930ad113afb7c80c88` |

Ignored outputs are under
`target/storage-android-smoke/rust/<target>/release/examples/storage_smoke`.
The byte audit reuses the existing tested ELF alignment checker and verifies
matching machine (62/183), ELF64 ET_DYN, DF_1_PIE, `/system/bin/linker64`,
three LOAD segments at 16384-byte alignment with valid file/address congruence,
and shared dependencies only `libdl.so`, `libm.so`, `libc.so`.
There is no system `libsqlite3.so` dependency. Per-ABI JSON reports are written
beside ignored outputs; hashes describe these actual builds, not byte-identical
compiler reproducibility on all hosts.

This agent performed no emulator/physical-device execution. The coordinator
owns transferring/hash-verifying/running the final x86_64 binary on both
selected authorized emulators. ARM64 execution, a 16 KiB OS, physical storage
power-loss behavior and broader M04 recovery/turn acceptance remain unproven
by cross-builds. No production support profile or full milestone completion
is inferred.
